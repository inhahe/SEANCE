Script (signal + MIDI)

Home Graph Basics Pin Kinds Trigger Node MIDI Modulator

The Script node is one programmable node that does two jobs: it generates control signals (LFOs, envelopes, custom curves) you wire into any Param or Signal pin, and it can generate MIDI (arpeggios, sequences, generative patterns). You choose which — or both — by setting its I/O counts in the editor. It replaces what other DAWs split into "LFO", "Envelope", "macro-curve" and "MIDI script": there's one node, and the difference between an LFO and an envelope is just which repeat mode you pick, while turning it into a MIDI generator is just adding a MIDI output. Add one from Signal Shape → Script (signal + MIDI) in the right-click menu, wire its outputs into whatever you want to drive, and double-click the node to open the editor.

This single node merged the former separate Signal Shape and MIDI Script nodes. Old projects that contain a MIDI Script node still open and work; you just create everything from the one Script node now.

By design the node only runs when its output is actually wired into something. An idle, unconnected shape costs no CPU.

The editor opens in its own window that doesn't lock the rest of SEANCE — you can keep it open (along with several XY Pad or Control Bank editors) and keep playing, editing the graph, and riding multiple input nodes at once while the song runs. Close it any time; it doesn't need to be dismissed before you do anything else.

Deciding what it does: the I/O counts

Four settings near the bottom of the editor decide whether this is a signal generator, a MIDI generator, or both. Each one adds or removes pins on the node:

  • Signal inputs (s1..sN) — 0–16 incoming control pins, read in your program as s1, s2, … so other signals can drive the shape.
  • Signal outputs (o1..oP) — 1–16 outgoing control pins. Your program assigns o1, o2, … (and o1 defaults to the curve, so a plain LFO/envelope just needs one). This is the "make a control signal" half.
  • MIDI outputs — 0–16. Leave at 0 for a pure signal source (a classic LFO/envelope). Set it to 1 or more and your program can emit MIDI notes and controllers — see Generating MIDI below.
  • MIDI inputs — 0–16. Leave at 0 for no MIDI in (a pure signal-from-signals node); 1 (the default) gives the single MIDI In pin that feeds the note/vel/gate/freq variables; set it to 2 or more and the node grows MIDI In 1, MIDI In 2, … so several MIDI sources can come in on their own pins. Tell them apart with the idx value returned by midievent()/pollmidi() (1 = MIDI In 1, 2 = MIDI In 2, …); the note/vel/gate/freq convenience variables track the most recent note across all inputs.
  • Pin type — flips all the continuous pins between Signal (blue) and Param (orange). They carry the same values and convert freely on the wire, so this is just which colour they present as.

So: 0 MIDI outputs = an LFO/envelope; a MIDI-emitting program with the signal output unused = a MIDI generator; both at once = a hybrid (say, an arpeggiator that also outputs an envelope).

What it outputs: a 0–1 signal

Each signal output is a control signal between 0 and 1, the standard range every control signal in SEANCE uses. 0.5 is the neutral "no change" level: an output sitting at 0.5 leaves whatever it's wired to exactly where you set it, 1 pushes that parameter all the way up, 0 all the way down. That's why a brand-new, layer-less shape rests at 0.5 — it does nothing until you give it a contour.

You mostly don't have to think about this: drop in a layer and the drawn shape's height maps straight onto 0–1, and curve (the variable that plays your drawing) is already 0–1. The one thing to watch is when you type your own formula in the Output box using trig: sin, cos and tan swing from −1 to 1, so a bare sin(...) would spend half its time below 0 and get clipped flat. Two easy fixes:

  • Use the unipolar versions: usin, ucos, utan (and usaw, usquare, utriangle) — same wave, already mapped into 0–1.
  • Or wrap a whole expression in unipolar(...), which maps −1..1 → 0..1. (bipolar(x) goes the other way if you ever need it.)

The four pieces of a shape

Every signal shape has four pieces. The first one is the only one you have to set; the rest have sensible defaults.

  1. A shape — the curve over time, built as a stack of layers exactly like the wavetable editor. Each layer is a parametric oscillator (sin, tri, saw, …), or breakpoint curve points, or a freehand drawing, or a math expression in the variable t (where t goes from 0 to 1 over one shape pass). Click + Layer to add layers; they're summed together, and a Sum of all layers preview under the stack shows the combined contour. A brand-new shape has no layers and outputs a flat 0.5 (neutral) until you add one.
  2. A repeat mode — what happens after the shape reaches the end of its pass. Three options: Don't repeat (one-shot, holds the last value forever — this is an envelope), Repeat forever (loops continuously — this is an LFO), Repeat N times (loops N times then holds, useful for "three pulses then stop").
  3. An optional trigger expression — a one-line expression that, when it becomes non-zero, restarts the shape from t = 0. If you leave it blank, the shape starts at app start and just runs.
  4. An optional set of signal inputs — extra Signal pins on the node that feed your shape and trigger expressions as variables s1, s2, … so any value flowing in the graph can drive the shape.

Make an LFO

A fresh Signal Shape is set up as an LFO — repeat forever, no trigger — but it starts neutral: it has no layers, so it outputs a constant 0.5 (neutral) and won't sweep anything until you give it a contour. The editor opens showing an empty layer stack with a + Layer button and a hint. Click + Layer to add your first layer (it comes in as a sine), then on that layer's row pick Sine / Saw / Square / Triangle / Drawn / Formula, or draw the curve by hand. Add more layers to sum several shapes into one (e.g. a slow sine plus a fast ripple) — the Sum of all layers preview shows the result. Then wire Signal Out to (for example) a synth's filter cutoff Param pin and you have vibrato-style modulation.

Setting the speed

How fast the shape cycles is shown two equivalent ways in the editor, side by side: Cycle length (how long one cycle takes) and Rate (how many cycles per unit time). They're the same setting — Rate = 1 ÷ Cycle length — so editing one updates the other; the = between them is the reminder. Use whichever feels natural: "I want a cycle every 2 seconds" → type 2 in Cycle length; "I want 0.5 Hz" → type 0.5 in Rate. You get the same LFO either way.

The Sync to beat toggle next to them decides the units:

  • Off: Cycle length is in seconds, Rate is in Hz (cycles per second). The LFO's speed ignores the song tempo.
  • On (tempo-locked): Cycle length is in beats, Rate is in cycles per beat. The LFO speeds up and slows down with the song tempo — so a 1-beat cycle stays locked to the groove no matter the BPM.

Rate and Sync to beat are also the first two sliders on the node's face in the graph, so you can nudge the speed without opening the editor; the editor fields and the face sliders always stay in agreement.

Locked to the song, or free-running

Underneath the speed row is a checkbox: Free-run (ignore song position). It decides what clock the LFO runs off — which matters for whether your song sounds the same every time you play it:

  • Off (the default): the LFO's position is locked to the song position. Press play from the same spot and the LFO is always at the same point in its cycle, so what you hear matches what gets exported, and replaying a section sounds identical every time. While playback is stopped, the LFO holds still (and follows the playhead if you scrub).
  • On: the LFO runs continuously off its own clock, like an old analog synth's LFO — always moving, even when the song is stopped, and drifting independently of the song. It feels alive, but it's not reproducible: a bounce can come out different from what you heard, and two playthroughs won't match.

Leave it off unless you specifically want that never-stopping, free-floating wobble. (This checkbox does nothing once you set a Trigger — see below — because a triggered shape already restarts cleanly on every trigger, so it's greyed out in that case.)

Common LFO shape expressions:

  • sin(t * 2*pi) — sine wave.
  • tri(t) — triangle.
  • saw(t) — saw ramp from -1 to 1.
  • 2*(t<0.5)-1 — square (uses a comparison: 1 when t<0.5, 0 otherwise, then rescaled to ±1).
  • random(floor(t*8)) — sample-and-hold: 8 random steps per cycle.

Make an envelope

An envelope is just a shape with repeat = Don't repeat and a trigger expression that fires on note-on. Set:

  • Shape: something like exp(-t*4) for a fast decay, or use the curve editor and draw an ADSR-looking contour.
  • Repeat: Don't repeat.
  • Trigger: gate — fires whenever a MIDI note arrives on the MIDI In pin.

Wire MIDI In to your MIDI source and Signal Out to (for example) a synth's amp envelope. Every note-on resets the shape's t to 0 and plays the curve from start to end, then holds the final value.

Trigger expressions

The trigger expression is evaluated every sample. Whenever it transitions from zero (or negative) to non-zero (positive), the shape restarts. Some useful trigger expressions:

  • gate — fires on every note-on. (gate is 1 while any note is held, 0 otherwise; the rising edge fires.)
  • vel > 0.7 — fires only when the note's velocity is above 0.7 (0–1 range). Great for accent envelopes that only play on hard hits.
  • note == 60 — fires only on middle C.
  • s1 > 0.5 — fires when signal input s1 crosses 0.5. Lets you chain shapes: one shape's output triggers the next.
  • (blank) — never fires from a trigger, so the shape just runs free.

The Manual Trigger button in the editor fires the shape immediately regardless of the expression — handy for previewing while editing.

Signal inputs (s1, s2, …)

Click Signal inputs: in the editor and bump it from 0 up to however many extra inputs you need (up to 16). The node grows new Signal In pins named s1, s2, … in order, and you can reference those values directly in both the shape expression and the trigger expression as the variables s1, s2, etc.

Examples (in the expression box):

  • FM the LFO with another LFO: usin(t * 2*pi + s1 * 4) — input s1 modulates the phase. (usin, not sin, so the result stays in 0–1.)
  • Amplitude blend: usin(t*2*pi) * s1 + usaw(t) * (1 - s1) — input s1 crossfades between a sine and a saw.
  • External gate: trigger = s1, with another signal wired into the s1 pin — that signal's rising edges retrigger the shape. Wire a Trigger node's Signal Out into s1 for per-note-conditional retriggers.

Reading the drawn shape from an input: shape(pos)

There's an important distinction between two ways to read your drawn shape:

  • curve reads the drawing at the node's own running phase. It's the LFO/envelope contour playing out over time. You don't choose where in the drawing it reads — the node's clock does.
  • shape(pos) reads the drawing at a position you compute. Now you decide where in the drawing to look, sample by sample.

This matters when you want an input signal to index into the drawing rather than just scale it. Picture the drawing as a lookup curve (a transfer function) and the input as the thing sliding a finger along it:

  • Waveshaper: shape(s1) — input s1 sweeps through the drawn curve. Wire an LFO or an audio-rate signal into s1 and the drawing reshapes it.
  • Phase warp: shape(x + s1*0.1) — play the drawing at the normal rate but nudge the read position with the input.
  • Read across the whole drawing: shape(s1) — inputs are already 0–1, so an input sweeping its full range reads across the entire drawing once.
  • Double-speed read: shape(t * 2) — ignore the node's phase and scan the drawing yourself.

The position you pass to shape() is a 0..1 phase that wraps around — so 1.25 reads the same place as 0.25, and negatives wrap too. That's the key to why there's no "the input is infinite but the drawing is finite" conflict: the drawing is never addressed by an absolute sample number. It's addressed by a normalized 0..1 position, and any continuous value — the node's clock, an input signal, or your own math — can supply that position. shape(x) is exactly equivalent to curve.

MIDI variables

If you wire MIDI into the node's MIDI In pin, the following variables are available in both shape and trigger expressions:

  • gate — 1 while at least one note is held, 0 otherwise.
  • note — MIDI note number (0–127) of the most recent note-on.
  • freq — frequency in Hz of the most recent note-on.
  • vel — velocity (0–1) of the most recent note-on.

Use them to make the shape react to the note. E.g. Output = usin(t * 2*pi) * vel makes the LFO depth scale with how hard the note was played. (usin keeps the result in 0–1; a bare sin would clip its lower half.)

Generating MIDI

This is the programmatic, time-driven way to make MIDI: a program that runs on the clock and emits arpeggios, sequences, or generative patterns. If instead you just want to decorate notes you play — harmonies, octaves, chords, flams, probabilistic ghost notes, or note generation from an audio threshold — reach for the rule-based Trigger node, which does all of that by filling in form fields with no scripting.

Set MIDI outputs to 1 (or more) and the node grows a MIDI Out pin and your program can emit MIDI live. Now the "Output" box is a little program that runs every sample; instead of just returning a number it can do things:

  • note(pitch, vel, durSec) — play a note now and release it after durSec seconds. pitch is a MIDI number or a name like "C4"; vel is 0–127.
  • noteon(pitch, vel) / noteoff(pitch) — start and stop a note yourself.
  • cc(number, value) — send a controller (value 0–1).
  • bend(value) — pitch bend (value −1..1, 0 = centre).

Variables you assign stay set between samples, so you can keep a step counter or phase. A four-on-the-floor kick is just:

ph = beat - floor(beat)
(ph < dt*bpm/60) ? note(36, 110, 0.1) : 0

If you add several MIDI outputs, pick which one the next emits go to by setting out (0 = MIDI Out 1, 1 = MIDI Out 2, …). Each output is its own independent cable, so you can split a kick to one synth and a snare to another:

out = 0; (ph < dt*bpm/60) ? note(36, 110, 0.1) : 0
out = 1; (frac(beat*2) < dt*bpm/60) ? note(38, 90, 0.1) : 0

Pressing Stop always silences any notes the program left hanging. And because signal and MIDI run in the same pass, one program can both o1 = curve * vel (an envelope out the signal pin) and note(...) (an arpeggio out the MIDI pin) at once. For the full MIDI vocabulary — sections (init:/start:/loop:), all the variables, note names, and the Lua/WebAssembly options — see the Script program reference in REFERENCE.md.

Presets

Each layer row has the same preset menu as the wavetable / layered-waveform editor — common LFO and envelope curves you can load as a starting point and then tweak. Pick a preset on a layer's row and that layer's shape and curve points are replaced with the preset's contents. Your other layers, repeat mode, trigger expression, and signal-input count are not touched, so you can swap one layer's contour without losing the rest of your setup.

Params on the node face

Four params live on the node itself, exposed as Param pins so you can modulate them with other shapes:

  • Rate — how fast the shape runs. In free mode it's in Hz (cycles per second); with Beat Sync on it's read as beats per cycle so the shape locks to the transport tempo.
  • Beat Sync — 0 = free-running (Rate in Hz), 1 = synced to the transport (Rate in beats per cycle).
  • Phase — phase offset, 0..1, shifts where in the cycle the shape starts.
  • Output — read-only readout of the shape's current value, exposed as a pin so you can chain it.

Scripting it: Built-in, Lua, or WebAssembly

By default the "Output" box uses SEANCE's little expression language. The Language dropdown at the top of the editor swaps in a full programming language for the same node:

  • Built-in (default) — the expression that turns curve into the output, as described above.
  • Lua, per sample — the "Output" box becomes a small Lua program. Write a loop() that returns the output value each sample. You can still read curve (the drawn shape at the current phase) and every variable above, so the drawing, trigger, repeat and speed all keep working — you've just upgraded the output formula to a real language. Example: function loop() return curve * (0.5 + 0.5*sin(t*31.4)) end.
  • Lua, per block or WebAssembly — raw mode: your script fills the whole signal itself, sample by sample (Lua: out(i, value) for i = 0..n-1). The drawing's phase, trigger, repeat and speed controls no longer apply and are greyed out — but you can still sample the drawing with shape(pos) and read inputs with sig(k, i). This is the mode for fully custom, sample-accurate signal generation. The program runs once per audio block — a handful of times a second — instead of being re-evaluated for every single sample, so it scales to many instances. A WebAssembly module is itself a loop-owning program just like stream() below: it keeps its state in memory across blocks, drives every output pin independently, and (if the node has a MIDI input) can read incoming MIDI events — and because it owns its loop, the Run dropdown doesn't matter for it. WASM is very fast and never re-instantiated between blocks, so it's a good choice for heavy custom DSP.

Streaming (stream()) — instead of loop(), a Lua program can define function stream() and write itself as one continuous loop. It pulls input and pushes output at its own pace, and SEANCE quietly pauses it at the block boundary and resumes it when the next block of audio is ready — so you never think about blocks at all, and any local variable you keep (a filter's state, a delay line, a running phase) survives from one block to the next for free. (Streaming is sample-accurate by nature, so the Run dropdown doesn't matter for a stream() program — it runs the same way whichever rate is selected.) A one-pole low-pass is just:

function stream()
  local y = 0
  while true do
    local x = pull()       -- next input sample (waits for the next block when needed)
    y = y + 0.05*(x - y)   -- y carries over between blocks automatically
    out(y)                 -- write this sample
  end
end

The toolkit: pull() (wait for the next input sample — returns one value per input pin), poll() (grab one if ready, else nil), wait() (hand the block back), out(v) (write the current sample to the first output), the whole-block forms pullblock() / pollblock() / outblock(t), and pollmidi() for event-driven MIDI (below). A streaming node can have any number of inputs and outputs: drive each output independently with out(n, v) (or outblock(n, t)) where n is the 1-based pin o1, o2, …, and read every input together — local a, b = pull(), or local params = pullblock() where params[k] is the array of input pin k's samples. The Lua reference button has the full list with examples.

In any per-block program you can consume MIDI as events rather than just reading the current held note. In a loop() program: midiin() tells you how many MIDI events arrived this block, and midievent(k) (for k = 1..midiin()) returns kind, offset, a, b, idx — where kind is "on", "off", "cc" or "bend", offset is the sample position within the block, a/b carry the note/velocity (or controller/value, or bend amount), and idx is which MIDI input pin it arrived on (1 = MIDI In 1, 2 = MIDI In 2, …; always 1 with a single input). In a stream() program, call pollmidi() inside your loop instead: it hands you the next event (same kind, offset, a, b, idx) the moment the cursor reaches it, or nil when none is due yet. Either way a script can react to each note-on and note-off at the exact sample it happened. (See the Lua reference button for worked examples.)

The Run dropdown (per sample / per block) is only adjustable for Lua; the built-in language is always per-sample and WebAssembly is always per-block. With Lua selected, the Lua reference button shows the full model and examples.

Tip: the same Signal Shape node can act as both an LFO and an envelope depending on which output you wire — set repeat = Repeat forever and a high-gate trigger, and the shape will run continuously between notes (LFO behavior) but also reset on each note-on (envelope behavior). One node, two roles.
