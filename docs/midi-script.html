This is a mode of the Script node. Generating MIDI by program used to be a separate "MIDI Script" node; it's now just what the unified Script (signal + MIDI) node does when you give it one or more MIDI outputs. This page is the program tutorial — see the Script page for the node, its I/O counts, and the signal-generation half. Old projects with a standalone MIDI Script node still open and work.

You can make the Script node generate MIDI by running a tiny program you write — a drum machine, a generative sequencer, an arpeggiator, an LFO-to-CC, a chord exploder, whatever you can express in a line or two of maths. The program runs once for every audio sample and emits MIDI live, so it stays perfectly in time and reacts instantly to the transport and to incoming signals.

You don't need to install anything or know a "real" programming language — the script is the same little expression language used elsewhere in SEANCE (the same sin, noise, floor, ?: you'd type into a signal shape), with a few extra things bolted on: you can write several statements, remember values between samples, and call functions that emit MIDI.

Add a Signal Shape → Script (signal + MIDI) node from the right-click menu, then in the editor set MIDI outputs to 1 (or more). The editor opens automatically; double-click the node (or right-click → Edit Script…) to reopen it later. Wire the node's MIDI Out into any synth.

Your first beat

Type this into the program box:

ph = beat - floor(beat)
(ph < dt*bpm/60) ? note(36, 110, 0.1) : 0

Press play. You'll hear a kick drum (MIDI note 36) on every beat. Here's what each piece does:

  • beat is the transport position counted in beats. floor(beat) chops off the fraction, so ph is "how far into the current beat we are", from 0 up to 1.
  • The second line fires a note only in the tiny window right at the start of each beat (dt*bpm/60 is the length of one sample expressed in beats). The ? … : 0 is an "if": emit the note when the condition is true, otherwise do nothing.
  • note(36, 110, 0.1) plays note 36 at velocity 110 for 0.1 seconds, then releases it automatically.

Add a random hi-hat by appending another line:

(noise(0) > 0.6) ? note(42, 60, 0.05) : 0

Emitting MIDI

These functions push MIDI at the current instant. Pitch and velocity are 0–127.

  • note(pitch, vel, durSec) — play a note that releases itself after durSec seconds. The easiest one to use.
  • noteon(pitch, vel) / noteoff(pitch) — start and stop a note yourself, when you want to control the length by hand.
  • cc(number, value) — a control-change message. value runs 0–1 (it's scaled to MIDI's 0–127 for you). Great for sweeping a filter: cc(74, 0.5 + 0.5*sin(t)).
  • bend(value) — pitch bend, where value goes from −1 (down) through 0 (centre) to +1 (up).

Note names instead of numbers

If you'd rather not remember that middle C is 60, you can write the name in quotes anywhere a pitch goes: note("C4", 100, 0.5) is exactly the same as note(60, 100, 0.5). Names use a letter A–G (upper or lower case), optional sharps (#) or flats (b), and an octave number — "C4", "c#4", "Bb3". (C4 = 60, A4 = 69; leave the octave off and it assumes 4.)

Two helpers convert for you:

  • notenum("C4") → 60 — name to number (so you can do maths on it, e.g. note(notenum("C4") + 7, …) for a fifth up).
  • notefreq("C4") or notefreq(60) → the frequency in Hz, using whatever tuning system the project is set to (Settings → Tuning) rather than always-standard tuning. (In Lua there's also notename(60) → "C4", the reverse of notenum; the built-in language can't return text so it doesn't have that one.)

Remembering things between samples

Any variable you assign with = keeps its value the next sample, and the next, forever — so you can build up state over time without any special syntax. A simple step sequencer that advances a counter on each beat:

ph = beat - floor(beat)
hit = ph < dt*bpm/60
hit ? (step = (step + 1) % 4) : 0
hit ? note(48 + step*3, 100, 0.2) : 0

Here step survives from one note to the next, walking 0,1,2,3,0,1,… and choosing the pitch. (Variables start at 0 the first time, and reset whenever you edit the program.)

Running something once: init: and start:

Because the program runs every sample, forever, there's no obvious place to do something a single time — like play one note at the very beginning, or set up a table before the music starts. Two optional section headers solve this. Put one on a line by itself and everything below it (until the next header) becomes that section:

  • init: runs once when the program loads or whenever you edit it. Use it to seed persistent variables — a starting step, a random seed, a lookup table. Emit functions here do nothing (init is for setup, not sound).
  • start: runs once each time playback starts from stop, right on the downbeat. Unlike init it can emit, so it's the place for a one-shot: a single note, a chord, a reset CC.
  • loop: is everything else — the per-sample body you've been writing all along. Any lines before the first header are loop by default, so a program with no headers behaves exactly as before.

All three sections share the same persistent variables, so init: can set a counter that loop: reads and start: resets. A program that plays one chord at the downbeat and then stays silent is just:

start:
note(60, 100, 1.0)
note(64, 100, 1.0)
note(67, 100, 1.0)

And a sequencer that always begins from step 0 every time you hit play:

init:
step = 0

start:
step = 0

loop:
ph = beat - floor(beat)
hit = ph < dt*bpm/60
hit ? (step = (step + 1) % 4) : 0
hit ? note(48 + step*3, 100, 0.2) : 0

Reading the world

Your program can read a handful of built-in values every sample:

  • t — seconds since the song started; beat, bar — musical position; bpm — tempo; playing — 1 while playing.
  • dt — the length of one sample in seconds; sr — the sample rate.
  • note, vel, gate, freq — the most recent note arriving at the node's MIDI In pin (its number, velocity 0–1, whether a key is held, and its pitch in Hz). Use these to react to what you play. If the node has several MIDI inputs (see below), these track the most recent note across all of them.
  • s1, s2, … — Signal input pins (see below).

The full maths toolbox is available too: sin cos tan asin acos sinh cosh atan asinh acosh atanh sqrt inversesqrt abs sign exp exp2 log log2 pow tanh saw square triangle noise floor ceil round roundEven trunc fract mod min max clamp mix step smoothstep fma radians degrees if, comparisons (< > == …), and && || !. (These match the GLSL shaping functions — the complete scalar set of GLSL's trig/exponential/common builtins — so the same idioms carry over.)

Signal inputs and a drawn shape

The editor has two spinners and an optional shape:

  • Signal inputs (s1..sN) — dial this up to add amber Signal input pins. Wire an LFO, envelope, or XY-pad output into them and read them as s1, s2, … For example cc(1, s1) turns an incoming signal into mod-wheel data.
  • Shape — an optional hand-built curve (the same layer editor used for wavetables). Sample it anywhere with shape(pos), where pos runs 0→1. Use it as a velocity contour, a melody table, or a probability curve. Until you add a layer it just returns 0.

Multiple outputs — one cable per drum

A real drum kit wants the kick, snare, and hat going to different places. Turn up MIDI outputs to give the node several output pins ("MIDI Out 1", "MIDI Out 2", …), then choose where each note goes by setting out before you emit:

out = 0;  note(36, 110, 0.1)
out = 1;  note(38, 90, 0.1)
out = 2;  note(42, 60, 0.05)

Each output is its own independent MIDI cable (numbered from 0 in the script, shown as "MIDI Out 1" upward on the node) — not a MIDI channel you have to manage. Wire each one to a different drum instrument.

Multiple inputs — merge or split incoming MIDI

The mirror image: turn up MIDI inputs in the editor to give the node several input pins ("MIDI In 1", "MIDI In 2", …), each its own cable. When you read events with midievent() (or pollmidi() in a streaming program) the last value it returns is idx — which input the event came in on (1 = MIDI In 1, 2 = MIDI In 2, …):

for k = 1, midiin() do
  local kind, offset, a, b, idx = midievent(k)
  if kind == "on" then
    if idx == 1 then -- handle keyboard
    elseif idx == 2 then -- handle a drum pad
    end
  end
end

Like the outputs, each input is an independent cable, not a MIDI channel you manage. Leave MIDI inputs at 1 (the default) for the usual single MIDI In pin, set it to 0 if the node takes no MIDI at all, or higher to split sources apart. The note/vel/gate/freq convenience variables always reflect the most recent note across every input.

Choosing a language: Built-in, Lua, or WebAssembly

Everything above uses the built-in expression language — no setup, always real-time-safe. When your idea outgrows one-liners, the Language dropdown at the top of the editor switches the same node to a full programming language:

  • Built-in (default) — the little expression language. Runs once per sample.
  • Lua — a complete scripting language. Write a loop() function (it runs each sample or each block) plus optional start(); any top-level code runs once at the start. You get loops, tables, functions, and the same emit calls (note, cc, …). A second Run dropdown picks Per sample (sample-accurate, but heavy code can stutter the audio — the editor warns you) or Per block (much cheaper; for tight timing you pass a sample offset as the last argument, e.g. note(36,110,0.1, i) inside a for i=0,n-1 loop).
  • WebAssembly — load a .wasm module you compiled from C, Rust, Zig, or AssemblyScript. The editor shows a Choose .wasm file… button instead of the text box. Runs once per block.

A quick Lua version of the kick-drum beat:

function loop()
  local ph = beat - floor(beat)
  if ph < dt*bpm/60 then note(36, 110, 0.1) end
end

Click Language reference… with Lua selected to see the full Lua model and a sample-accurate per-block example.

Stuck for syntax? Click Language reference… at the bottom of the editor for the complete list of variables, functions, and examples (it switches to match the language you've picked). And remember the node is a generator: whatever MIDI you wire into it only sets the note/vel/gate variables — it is not passed through to the outputs.
